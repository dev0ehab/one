1 تعريفات سريعة

كل الحالات والأنواع المستخدمة في النظام مع قيمها النصية بالضبط (الـ enum constants).

BookingStatusEnum 5 قيم

newNEW — حجز جديد بانتظار القبول
pending_paymentPENDING_PAYMENT — مقبول، قيد الدفع
in_progressIN_PROGRESS — مدفوع، قيد التنفيذ
completedCOMPLETED — منتهي بنجاح

2 الفاعلون

CLIENT العميل

المستخدم النهائي. يتصفح مزودي الخدمة، يحجز، يدفع، يتابع حجوزاته، يقيّم، أو يلغي.

  • يسجل ويدخل عبر /api/client/*
  • حجوزاته تحت client/bookings
  • استفساراته تحت client/inquiries
  • محفظته تحت client/wallet

PROVIDER مقدم الخدمة

صاحب الخدمة. يستقبل الحجوزات، يقبل / يرفض، يصدر فواتير إضافية، وينهي الخدمة.

  • يسجل ويدخل عبر /api/provider/*
  • حجوزاته تحت provider/bookings
  • يلزم أن يكون is_approved=1 + is_active=true + is_blocked=false
  • يجب أن يمتلك اشتراكاً نشطاً في خدمة الحجز (hasActiveBookingService)
  • يدير إعلاناته وجدول عمله وحسابه البنكي
Sanctum guard مشترك: نفس الـ middleware auth:sanctum يخدم العميل والمزود — التمييز عبر check-auth-type:client وcheck-auth-type:provider التي تتحقق من نوع الـ model المرتبط بالـ token.

5 مخطط حالات الحجز (State Machine)

كل سهم يمثل انتقال محمي بـ endpoint محدد. أي محاولة انتقال خارج المسارات أدناه يردّها النظام برسالة booking_invalid_action.

stateDiagram-v2 direction LR [*] --> NEW : العميل ينشئ الحجز NEW --> PENDING_PAYMENT : المزود يقبل NEW --> CANCELLED : المزود يرفض أو العميل يلغي PENDING_PAYMENT --> IN_PROGRESS : العميل يدفع (wallet أو online) PENDING_PAYMENT --> CANCELLED : العميل يلغي IN_PROGRESS --> COMPLETED : المزود ينهي (بشرط عدم وجود فاتورة إضافية معلقة) IN_PROGRESS --> IN_PROGRESS : المزود يصدر فاتورة إضافية COMPLETED --> [*] : العميل يقيم اختياري CANCELLED --> [*]
ملاحظة مهمة حول الفاتورة الإضافية: لا يمكن للمزود إنهاء الحجز (complete) لو كانت الفاتورة الإضافية في حالة PENDING أو ACCEPTED أو PAYMENT_OVERDUE. لا بد أن تكون PAID أو REJECTED أو غير موجودة (null).

مخطط حالات الفاتورة الإضافية

stateDiagram-v2 direction LR [*] --> PENDING : المزود يصدر فاتورة إضافية PENDING --> ACCEPTED : العميل يقبل (تبدأ مهلة الدفع) PENDING --> REJECTED : العميل يرفض ACCEPTED --> PAID : العميل يدفع في المهلة ACCEPTED --> PAYMENT_OVERDUE : انتهت مهلة الدفع PAYMENT_OVERDUE --> PAID : العميل يدفع بعد انتهاء المهلة REJECTED --> PENDING : المزود يُعيد إصدار فاتورة جديدة PAYMENT_OVERDUE --> PENDING : المزود يُعيد إصدار فاتورة جديدة PAID --> PENDING : المزود يُصدر فاتورة إضافية أخرى

7 كل خطوة بالتفصيل

CLIENT   1. إنشاء الحجز POST client/bookings
Body
ad_id (required) — معرف الإعلان المراد الحجز منه
date (required) — تاريخ الحجز بصيغة Y-m-d (اليوم أو بعده)
time (required) — وقت الحجز بصيغة HH:MM
notes (optional) — ملاحظات max:2000 حرف
Auth
مطلوب (auth:sanctum + check-auth-type:client)
الشروط
- الإعلان (ad_id) نشط ومعتمد (status=approved)
- المزود المرتبط بالإعلان: is_active=true + is_approved=1 + is_blocked=false
- المزود لديه اشتراك نشط في خدمة الحجز (hasActiveBookingService)
- الفترة الزمنية (date + time) متاحة — لم تُحجَز من قبل وضمن ساعات عمل المزود
- لو التاريخ هو اليوم، الوقت يجب أن يكون في المستقبل
الناتج
سجل booking جديد + إشعار للمزود
الحالة
NEW
Code
app/Services/Entity/BookingService.php → store()
PROVIDER   2. المزود يرى ويتحقق من الحجز الجديد GET provider/bookings
Query
?status=new أو فلاتر أخرى حسب الـ BookingFilter
التفاصيل
GET provider/bookings/{id} — تفاصيل الحجز بما فيه: بيانات العميل + الخدمة + الموعد + السعر + الإعلان
الشرط
المزود مصادق عليه + هذا الحجز يخصه
PROVIDER   3. القبول أو الرفض POST provider/bookings/{id}/accept  |  POST provider/bookings/{id}/reject
الشرط
الحالة الحالية = new فقط — وإلا booking_invalid_action
القبول
لا body. الحجز ينتقل إلى PENDING_PAYMENT + إشعار للعميل (BookingAccepted)
الرفض
Body: reason (optional string). الحجز ينتقل إلى CANCELLED + يُحفظ cancel_reason + إشعار للعميل (BookingRejected)
CLIENT   4. الدفع POST client/bookings/{id}/pay
Body
payment_method ∈ {wallet, online}
الشرط
الحالة = pending_payment — وإلا booking_payment_not_required
فرع wallet
يُخصم المبلغ مباشرة من رصيد محفظة العميل (WalletService::deduct) → IN_PROGRESS + paid_at = now() + إشعار للعميل والمزود (BookingPaid). لو الرصيد غير كافٍ → insufficient_balance
فرع online
يُنشئ PaymentTransaction عبر بوابة الدفع النشطة → يعيد redirect_url + transaction_id. الحجز يبقى pending_payment لحين callback البوابة. بعد الـ callback الناجح → IN_PROGRESS + إشعار
لو السعر = 0
يُعامَل تلقائياً كـ wallet — ينتقل إلى IN_PROGRESS فوراً بدون خصم
PROVIDER   5. إصدار فاتورة إضافية (اختياري) POST provider/bookings/{id}/additional-invoice
Body
amount (required, numeric > 0) + reason (required, string)
الشرط
الحالة = in_progress + الفاتورة الإضافية الحالية ليست pending أو accepted (يمكن إصدار جديدة إذا كانت rejected أو paid أو null)
الناتج
الفاتورة الإضافية تُحفظ على الحجز + إشعار للعميل (BookingAdditionalInvoiceIssued)
CLIENT   6. الرد على الفاتورة الإضافية (اختياري) POST client/bookings/{id}/additional-invoice/accept  |  POST client/bookings/{id}/additional-invoice/reject
الشرط
الحالة = in_progress + additional_invoice_status = pending
القبول
لا body. تبدأ مهلة الدفع (افتراضي 72 ساعة من الإعدادات). الفاتورة → ACCEPTED
الرفض
Body: reason (optional). الفاتورة → REJECTED — يمكن للمزود إصدار فاتورة جديدة
CLIENT   7. دفع الفاتورة الإضافية (اختياري) POST client/bookings/{id}/additional-invoice/pay
Body
payment_method ∈ {wallet, online}
الشرط
الحالة = in_progress + additional_invoice_status ∈ {accepted, payment_overdue}
الناتج
نفس منطق الدفع العادي. عند النجاح → الفاتورة الإضافية → PAID
ملاحظة
إذا انتهت مهلة accepted دون دفع، يُحوَّل تلقائياً إلى payment_overdue عند أي request — لكن لا يزال بإمكان العميل الدفع
PROVIDER   8. إنهاء الخدمة POST provider/bookings/{id}/complete
الشرط
الحالة = in_progress — وإلا booking_invalid_action
شرط الفاتورة الإضافية
لا توجد فاتورة إضافية بحالة pending أو accepted أو payment_overdue — وإلا booking_pending_additional_invoice
الناتج
الحالة → COMPLETED + إشعار للعميل (BookingCompleted)
أثر
يفتح إمكانية التقييم للعميل
CLIENT   9. التقييم POST client/bookings/{id}/rate
Body
rate (required, integer 1..5) + comment (optional, max:1000)
الشروط
- الحجز يخص العميل
- الحالة = completed
- لم يُقيَّم سابقاً (يُرفض إذا كان rate موجود بالفعل)
الناتج
صف في جدول rates مرتبط بالحجز + تحديث متوسط تقييم المزود

8 المسارات الفرعية

أ. إلغاء العميل (Cancel)

متاح في الحالتين new وpending_payment فقط. بمجرد دفع العميل وانتقال الحجز إلى in_progress، يُغلق زر الإلغاء.

sequenceDiagram actor C as Client participant API actor P as Provider C->>API: POST client/bookings/{id}/cancel { reason } API-->>C: booking { status: cancelled } API-->>P: إشعار push — تم إلغاء الحجز Note over C,API: reason: string مطلوب، min:3، max:1000
شرط الإلغاء: يتحقق CancelBookingRequest من أن الحجز في حالة new أو pending_payment قبل وصول الطلب للـ service. لو الحالة in_progress أو completed أو cancelled → يُرفض بخطأ validation booking_cannot_cancel.

ب. رفض مقدم الخدمة (Reject)

متاح فقط في الحالة new. عند الرفض، ينتقل الحجز إلى cancelled.

PROVIDER   رفض الحجزPOST provider/bookings/{id}/reject
Body
reason (optional string) — سبب الرفض يُحفظ في cancel_reason
الناتج
الحجز → CANCELLED + إشعار للعميل (BookingRejected)

ج. دفع عبر بوابة خارجية (Online Payment)

عند اختيار payment_method=online، يعيد الـ API رابط redirect لبوابة الدفع الخارجية. بعد إتمام الدفع، البوابة ترسل callback للـ API فيحدّث الحجز تلقائياً.

sequenceDiagram autonumber actor C as Client participant API participant PGW as Payment Gateway C->>API: POST client/bookings/{id}/pay { payment_method: online } API->>PGW: إنشاء معاملة دفع PGW-->>API: transaction_id + redirect_url API-->>C: { redirect_url, transaction_id, booking } C->>PGW: يفتح redirect_url في browser PGW-->>C: صفحة الدفع C->>PGW: يُدخل بيانات البطاقة PGW->>API: callback بنتيجة الدفع API-->>C: إشعار push — booking { status: in_progress } Note over API: يحفظ payment_method + paid_at على الحجز
البوابات المدعومة: Myfatoorah, Hyperpay, Stripe, PayPal, Paymob, Telr, Clickpay, Alrajhi Bank — يتم اختيار البوابة النشطة من إعدادات النظام. المسار العام للـ callback: GET payment/get-payment-status/{brand_id}.

10 ملاحظات تقنية

نظام Sanctum + التمييز بين Client وProvider

الـ middleware auth:sanctum يخدم العميل والمزود بنفس الـ guard. التمييز يتم عبر middleware check-auth-type:client أو check-auth-type:provider الذي يتحقق من نوع الـ Eloquent model المرتبط بالـ token. لو أرسل العميل token لـ endpoint خاص بالمزود → يرد بـ 401 أو 403.

is-active Middleware

كل الـ endpoints المصادقة تمر عبر middleware is-active (بعد auth:sanctum) الذي يتحقق من:

  • الحساب غير محظور (is_blocked = false)
  • الحساب مُفعَّل (is_active = true)
  • البروفايل مكتمل — لو غير مكتمل يُعيد خطأ مع URL لإكمال البروفايل
DB Transactions

كل write يشمل أكثر من جدول يُلفّ داخل DB::transaction(). مثال: إنشاء الحجز + إشعار المزود. الدفع عبر المحفظة: خصم الرصيد + تحديث الحجز في معاملة واحدة لضمان التوافق.

Booking Number التلقائي

كل حجز يُنشأ تلقائياً له رقم فريد بصيغة BK-YYYYMMDD-XXXXXX (مثل BK-20260525-000123). يتم إنشاؤه عبر Observer أو في creating event على الـ Model.

تزامن حالة الفاتورة الإضافية (syncAdditionalInvoiceOverdue)

عند كل read لحجز (عبر findClientBooking أو findProviderBooking)، يُشغَّل syncAdditionalInvoiceOverdue() الذي يتحقق تلقائياً إذا انتهت مهلة الدفع لفاتورة بحالة accepted ويُحوِّلها إلى payment_overdue ويُرسل إشعاراً للعميل. هذا يضمن دقة البيانات دون الحاجة لـ scheduled job.

نظام الإشعارات

كل transition رئيسي يُطلق إشعار push عبر BookingNotificationService. أنواع الإشعارات:

  • BookingNewReceived — للمزود عند إنشاء حجز جديد
  • BookingAccepted — للعميل عند قبول المزود
  • BookingRejected — للعميل عند رفض المزود
  • BookingPaid — للعميل والمزود بعد إتمام الدفع
  • BookingCompleted — للعميل عند إنهاء الخدمة
  • BookingCancelled — للمزود عند إلغاء العميل
  • BookingAdditionalInvoiceIssued — للعميل عند إصدار فاتورة إضافية
  • BookingAdditionalInvoicePaymentDue — للعميل عند انتهاء مهلة الدفع
